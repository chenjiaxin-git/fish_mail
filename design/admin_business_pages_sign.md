> 目标：让商家通过 PC 后台完成日常看板查看、订单处理及首页轮播维护，复用已有交易规则。

## 1. 已确认范围

一次补齐三块：

1. 经营看板：今日订单、今日销售额、待处理订单分项及订单入口，补充后端聚合 API。
2. 订单管理：分页筛选、详情、称重报价、配送、完成、取消、登记人工退款和 Excel 导出，接通已有后端接口。
3. 轮播图管理：列表、新增/编辑、上传、跳转配置、排序、启停、软删除，补充缺失后端接口。

复用既有登录、分类、商品、库存页面与技术栈；保留修改密码入口。不新增多角色、多门店、会员、营销、财务对账、趋势大屏、外部配送或自动退款。

本次不启用真实微信支付、不重启业务服务、不操作生产数据。开发与浏览器验证使用隔离测试数据。

## 3. 经营看板

### 3.1 页面

- 路由 `/dashboard`；原 `/` 兼容跳转到看板，登录返回路径和鉴权守卫保持工作。
- 三张主指标卡：今日订单数、今日销售额、待处理订单数；待处理展示明确分项并可跳转订单筛选。
- 显示统计日期、最近成功刷新时间、手动刷新和错误重试，不把模拟固定数字当真实经营数据。
- 不引入图表库；沿用 Element Plus 卡片、统计数值、标签和表格样式。
- 修改密码入口保留在布局或看板，不能因替换欢迎页丢失。

### 3.2 已确认统计口径

| 指标 | 推荐口径 | 说明 |
| --- | --- | --- |
| 今日订单数 | sales_order.created_at 属于上海当日的全部订单数 | 含后来取消/关闭的订单，表示今日下单量 |
| 今日销售额 | payment_record.state=SUCCESS 且 paid_at 属于上海当日的 amount_cent 合计 | 按实际收款时间统计，不按创建日或完成日；不减人工退款 |
| 待处理订单数 | CREATED + PAID_WAIT_DELIVERY + DELIVERING + CANCELLED 且 refund_status=REQUIRED | 对应待报价、待配送、待完成、待登记退款；每单只计一次 |

销售额页面应说明“按今日成功收款统计，未扣人工退款”，避免把该数误解为净收入。当前没有退款金额及退款确认时间完整模型，不能自行计算净销售额。

QUOTED/PENDING_PAYMENT 在等用户确认/付款，建议不计入商家待处理；CLOSED、COMPLETED 不计入。待处理统计跨日期，不能只看今天新建的订单而遗漏历史未处理单。

### 3.3 API 与数据一致性

新增 `GET /api/v1/admin/dashboard`：

- 不接受客户端 userId、商户号或任意统计 SQL；由管理员 JWT 鉴权。
- 服务端使用 Asia/Shanghai 计算 `[今日零点,次日零点)`；同一 REPEATABLE_READ 一致性事务读取聚合数并记录管理端审计。
- data：date、todayOrderCount、todaySalesAmountCent、pendingOrderCount、pendingQuoteCount、pendingDeliveryCount、pendingCompletionCount、pendingRefundCount、generatedAt。
- 金额使用整数分。合计为 0 时返回 0，不返回 null；SQL 聚合不对支付记录与订单项做乘法式 JOIN，防止重复累计。
- 记录管理读取审计，与现有 admin_operation_log 风格一致；不记录敏感资料。
- 优先复用现有状态/时间索引，实施时检查聚合计划。如需要支付成功日期索引，新增 V9 迁移，不修改 V1～V8；本功能不新增业务数据表。

### 3.4 已确认刷新方式

看板及订单列表在页面可见时每 30 秒刷新，无重叠请求；页面隐藏、离开或登录失效时停止。手动刷新一直可用。

初次成功后后台刷新失败保留旧数据，显示未更新提示，不清零指标；避免每轮轮询弹重复错误 toast。重新可见时立即刷新。请求序号/取消机制防止旧响应覆盖新筛选。

订单详情打开报价、取消或退款表单时不自动覆盖草稿；提交前仍由服务端做版本/状态判断。后台提醒由待处理数及刷新体现，本次不新增声音或系统通知。

## 4. 订单管理

### 4.1 列表与筛选

- 路由 `/orders`，默认 page=1、pageSize=20，服务端分页，pageSize 最大 100。
- 筛选：状态、创建日期范围、完整订单号、完整收货手机号；沿用当前后端精确匹配语义，不把输入框误标为模糊搜索。
- 为看板待登记退款入口，建议增加可选 refundStatus（NONE/REQUIRED/MANUAL_REFUNDED），同步后端列表/count/导出查询。禁止仅过滤当前页数据伪装成全量筛选。
- 状态包含全部八种订单状态，明确区分“已取消”和“已关闭”。筛选条件可保存到 URL，刷新/返回仍恢复；改条件重置第一页。
- 列：订单号、创建时间、收货人/手机号、预估金额、最终金额、状态、退款状态、支付截止时间、详情入口。
- 未报价最终金额显示“待报价”；最终金额 0 显示 0.00，不回退为预估值。时间/金额/数量继续走集中格式化工具。
- 看板分项跳转对应状态或退款筛选，展示筛选标签，清空筛选可返回全量。
- 加载、无数据、网络失败、重试、分页越界均有明确反馈；变更后刷新当前列表和看板数据。

### 4.2 订单详情

建议独立路由 `/orders/:id`，便于刷新、直达和从列表返回。组件拆分基本信息、商品清单、报价记录、支付记录、状态日志和操作区域。

- 展示下单商品/地址快照，商品下架或地址修改不改变历史展示。
- 展示预估/实称数量、原单价、预估/最终金额、quoteVersion、报价期限、用户备注与取消原因。
- 改价历史将现有 itemsSnapshot 转换为类型安全的可读明细，不向商家直接展示原始 JSON；历史格式异常提示明细暂不可用，不阻塞其他详情。
- 支付记录和状态日志只读，展示必要的支付单号、微信交易号、金额、结果、时间及操作者来源；不展示支付签名、openid、密钥或加密回调原文。
- 人工退款凭证仅在管理员详情中展示；用户订单接口仍不暴露这些字段。
- ID 非法、不存在、401/403、状态变化等分别处理，不把异常堆栈显示给用户。

### 4.3 操作矩阵

| 状态 | 可操作 |
| --- | --- |
| CREATED | 填实称/最终金额并报价；取消 |
| QUOTED | 再次报价；取消 |
| PENDING_PAYMENT | 取消，先由后端查单/关单协调；不能改价 |
| PAID_WAIT_DELIVERY | 标记配送中；取消并进入待登记人工退款 |
| DELIVERING | 标记完成 |
| CANCELLED | refundStatus=REQUIRED 时登记已完成的人工退款 |
| COMPLETED/CLOSED | 只读 |

页面隐藏/禁用按钮只是交互辅助；真正权限、版本、支付、库存和状态判断都在现有后端 Service。

### 4.4 称重报价

- 弹窗或详情编辑区逐项显示预估数量与实称数量，包含所有原订单项，不允许新增/删除订单项。
- PIECE 实称为正整数，WEIGHT 最多三位小数，最小值沿用接口 0.001；最终金额非负整数分，原因必填最多 500 字。
- 商家在 UI 输入人民币元，提交时用十进制字符串严格转换为整数分，拒绝超两位小数和不安全整数；禁止浮点乘 100 后直接提交。
- 逐项金额可编辑，总额按整数分合计，前端用于提示，后端仍核对完整项与合计。可按实称×快照单价给出初始参考金额，但不覆盖商家已经编辑的金额。
- 提交携带当前 quoteVersion；QUOTE_VERSION_CONFLICT/状态变化时保留草稿供查看，刷新最新订单并要求重新确认，不能自动使用新版本重发旧报价。
- 金额为 0 时明确提示此金额无法发起微信支付，沿用已确认的零金额业务规则，不擅自将商家报价约束改成必须大于 0。
- 单次提交锁、防重复点击、成功后展示最新详情；失败恢复按钮，不在响应不确定时自动重复改价。

### 4.5 配送、完成、取消与退款登记

- 配送、完成操作二次确认，成功刷新详情；重复点击由前后端共同保证幂等。
- 未支付取消：必填原因，调用现有 cancel，微信结果不确定时显示后端 PAYMENT_PROCESSING 等提示，不自行当作已取消。
- 已支付取消：弹窗明确“系统不自动退款，需商家在微信商户平台原路退款后登记凭证”，禁止页面暗示点击即退款。
- 登记人工退款：仅 CANCELLED+REQUIRED，凭证必填最多 100 字；成功后 MANUAL_REFUNDED，复用已有按实称回补库存逻辑。
- 任何取消结果若服务端发现已支付，使用返回/重新查询的真实状态决定后续操作，不绕过支付协调。

### 4.6 Excel 导出

- 在订单列表提供导出入口；保留 `/orders/export` 可作为同一导出界面直达路由，不重复实现业务。
- 日期起止必填，按自然日闭区间最多 31 天；携带相同状态、订单号、手机号及可选退款状态筛选，服务端再次校验。
- 使用现有 `/api/v1/admin/orders/export`，后端生成 .xlsx；不在浏览器拼 CSV，不增加异步导出平台。
- 现有 Axios 拦截器假定所有成功响应是 ApiResponse。新增明确的 Blob 请求分支，仍经过 Token、401/403 和安全错误处理；成功二进制不做 body.code 校验。
- 下载前核对响应类型，JSON 错误 Blob 转换为中文错误提示，不能把鉴权失败/参数错误保存为 Excel。完成后释放临时对象 URL，按钮恢复。
- 继续复用现有导出字段、SXSSF 和审计；不借页面开发重写为新的报表或财务系统。

## 5. 轮播图管理

### 5.1 页面与 API

路由 `/banners`：分页列表、状态筛选、预览、新增、编辑、排序、启停、软删除。沿用 V5 shop_banner，默认按 sort ASC、id ASC，与小程序一致。

新增管理 API：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/v1/admin/banners | 分页查询，支持 ACTIVE/DISABLED 筛选 |
| GET | /api/v1/admin/banners/{id} | 编辑读取详情 |
| POST | /api/v1/admin/banners | 创建 |
| PUT | /api/v1/admin/banners/{id} | 编辑、排序及启停 |
| DELETE | /api/v1/admin/banners/{id} | 软删除，二次确认 |

请求字段：title、imageUrl、jumpType、jumpTargetId、sort、status；不接收 deleted 或操作者 ID。返回展示字段及创建/更新时间，不直接暴露数据库实体。

### 5.2 校验与跳转

- title 去首尾空白后 1～100 字；imageUrl 必填、最多 500 字，使用已有上传接口返回的安全图片地址约定。
- 上传复用 `/api/v1/admin/files`，沿用 jpg/png/webp、5MB、扩展名/MIME/魔数校验。页面不把图片原件写入仓库，不新增存储服务。
- sort 为非负整数，值越小越靠前；status 仅 ACTIVE/DISABLED。
- jumpType 仅 NONE、PRODUCT、CATEGORY；NONE 时 jumpTargetId 清空，后两者要求正整数目标 ID，且目标存在、未软删除。
- 建议启用轮播时额外要求目标商品已上架或分类已启用；后台目标选择使用现有分页接口，不能一次无限加载全部商品。
- 已启用轮播的目标后来下架/删除，不自动篡改商品或联动启停轮播；后台展示目标不可用提示，商家可改目标或停用，小程序继续沿用现有不可访问处理。
- 不新增外部网页、自定义链接或营销活动跳转类型。图片地址不支持 javascript/data 等执行型协议，后端不下载客户端提供的远程 URL。
- 管理操作均鉴权、服务端校验和写 operation_log；停用/删除后不再出现在公开 ACTIVE 查询中，已下载的小程序内容以下次刷新为准。
- 列表与表单有图片失败占位、空态/错误重试、上传/保存锁；删除图片不级联物理删文件，避免误删仍被商品或其他轮播引用的资源。
