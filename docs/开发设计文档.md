## 0. AI 开发须知

本文是项目实现约束，不是可选建议。执行开发任务时必须遵守以下规则：

1. 先阅读第 2 节技术栈、第 5 节数据模型、第 6 节接口设计和第 7 节页面设计，再开始编码。
2. 金额只使用整数分计算和传输；数据库使用 BIGINT，禁止使用浮点数计算金额。
3. 重量和称重数量使用 DECIMAL，禁止用 DOUBLE。
4. 订单状态只能通过本节规定的状态机变更，禁止在多个 Service 中直接覆盖订单状态。
5. 库存预占、支付确认、取消释放必须具有幂等性，并写入库存流水。
6. 微信支付回调必须验签、校验商户号和金额、处理重复通知，不能仅凭客户端回调更新订单。
7. 已支付订单不得修改金额；支付后取消只允许人工原路退款并登记结果。
8. 所有后台接口必须鉴权；所有列表接口必须限制分页上限；所有写接口必须做服务端校验。
9. 不实现会员、优惠券、营销、多门店、多角色、短信、骑手、地图轨迹和动态补差。
10. 每完成一个模块，都必须补齐对应测试并通过“完成定义”，不得只生成页面或接口外壳。

开发推荐顺序：

~~~text
数据库与迁移 -> 后端公共层 -> 用户/认证 -> 商品与库存
-> 购物车/地址 -> 订单与称重改价 -> 支付与回调 -> 后台管理页面
-> 小程序页面 -> 通知 -> 部署 -> 联调与验收
~~~

## 1. 项目范围与设计原则

### 1.1 业务范围

系统服务线下卖鱼门店，包含客户微信原生小程序和商家 PC 管理后台。客户浏览商品、提交预订单，商家确认并按实际称重修改数量和金额，客户确认最终金额后通过微信支付。商家自行安排配送，不接入快递、骑手或地图平台。

一期交付：

- 微信小程序：登录、首页、分类搜索、商品详情、购物车、地址、下单、改价确认、微信支付、订单查询、订阅消息。
- PC 管理后台：单管理员登录、看板、分类、商品、库存、轮播图、订单处理、称重改价、订单导出。
- Java 后端：业务接口、微信登录、微信支付 APIv3、文件存储、订单状态机、库存、定时任务、审计和通知。
- MySQL 数据库、Flyway 迁移脚本、Docker Compose 部署文件、部署文档和商家手册。

不在一期范围：

- 会员、积分、会员价、优惠券、满减、限时特价、拼团。
- 支付后改价、自动补差、自动退款、部分退款。
- 多门店、店员账号、角色权限、客户评价、短信、小票打印。
- 骑手应用、地图定位、配送轨迹、动态配送费。
- 复杂 BI、财务对账和长期销售报表。

### 1.2 设计原则

- 稳定优先：先保证下单、改价、支付、库存和订单流转闭环。
- 服务端裁决：状态、库存、价格、权限均以数据库和服务端为准。
- 可追溯：订单金额、改价、支付、库存、状态变化全部留痕。
- 幂等优先：重复请求、重复支付回调、定时任务重复执行不能产生重复副作用。
- 简单部署：一个后端服务、一个管理端静态站点、一个小程序端和一个 MySQL 实例。
- 可替换外部服务：对象存储和微信支付通过接口适配，业务层不直接依赖厂商 SDK 类型。

## 3. 业务规则

### 3.1 商品和规格

商品可以有多个规格，例如“草鱼/整条”和“草鱼/按斤”。规格包含计价方式：

- PIECE：按件销售，数量必须为正整数。
- WEIGHT：按重量销售，数量允许三位小数，默认单位 kg。

关键规则：

1. 商品价格是下单时固定单价，商家仅能通过修改实称数量和最终金额完成称重改价。
2. 金额计算以“分”为单位。预估金额 = 预估数量 × 单价；最终金额必须由商家明确填写并被服务端重新校验。
3. 规格单价、名称和单位会在下单时复制到订单项快照，商品后续改名不影响历史订单。
4. 商品或规格下架后不可加入购物车或下单。
5. 商品库存以规格为粒度。可用库存 = physical_stock_qty - reserved_qty。
6. 库存预警条件为可用库存小于等于 warning_qty；后台列表需要显示预警标识。
7. 分类只有在不存在有效商品时才能物理删除；否则返回“分类下仍有商品”。

### 3.2 购物车

- 购物车按用户和规格保存 quantity。
- 增加数量时服务端校验规格状态、最小购买量、步进值和可用库存。
- WEIGHT 规格数量允许小数，步进值默认 0.5 kg；PIECE 规格数量只允许整数。
- 结算时仅提交客户端选中的 cart_item_ids，服务端重新读取价格和库存。
- 若商品下架、删除或库存不足，返回逐项错误，用户处理后重新提交。

### 3.3 地址

- 字段：联系人、手机号、详细地址、是否默认。
- 手机号使用中国大陆手机号校验，可扩展但一期不强制实名认证。
- 每个用户最多保存 20 个地址；删除为物理删除。
- 下单时把地址复制到订单快照，历史订单不随地址修改而改变。
- 用户只能查询和操作本人地址。

### 3.4 下单和称重改价

下单请求包含地址、收货备注、订单项和客户端幂等键。下单后商品总价只是预估价，用户在商家改价确认前不能支付。

商家改价规则：

1. 只允许调整订单项的实称数量和最终金额，并填写改价原因。
2. 每次改价生成新 revision_no，保存调整前后总额和改价人，禁止覆盖历史记录。
3. 最终总额必须等于订单项最终金额之和；服务端根据 revision_no 做乐观锁，避免旧页面覆盖新改价。
4. 改价后订单进入 QUOTED，向用户发送订阅消息“商家已称重改价”。
5. 用户点击“确认价格并支付”后，订单进入 PENDING_PAYMENT，系统创建微信预支付单。
6. 只有 PENDING_PAYMENT 可以调用预支付；其他状态返回当前状态错误。
7. 支付成功后金额锁定，禁止再次改价。
8. 支付后订单取消由商家在微信商户平台人工原路退款，后台必须登记退款状态和凭证；一期不调用微信退款接口。

### 3.5 订单状态机

| 状态 | 用户展示 | 允许触发 | 可转至 |
| --- | --- | --- | --- |
| CREATED | 待商家确认 | 商家改价/商家取消/超时关闭 | QUOTED、CANCELLED、CLOSED |
| QUOTED | 待支付 | 用户确认价格、用户取消、商家取消、超时关闭 | PENDING_PAYMENT、CANCELLED、CLOSED |
| PENDING_PAYMENT | 待支付 | 微信支付成功、用户/商家取消、超时关闭 | PAID_WAIT_DELIVERY、CANCELLED、CLOSED |
| PAID_WAIT_DELIVERY | 待配送 | 商家标记配送中、商家取消并人工退款 | DELIVERING、CANCELLED |
| DELIVERING | 配送中 | 商家标记完成 | COMPLETED |
| COMPLETED | 已完成 | 无 | 无 |
| CANCELLED | 已取消 | 无 | 无 |
| CLOSED | 已关闭 | 无 | 无 |

附加状态规则：

- CREATED 超过 order.confirm.timeout-minutes（默认 1440 分钟）自动 CLOSED。
- QUOTED 或 PENDING_PAYMENT 从 quoted_at 起超过 order.payment.timeout-minutes（默认 60 分钟）自动 CLOSED。
- 关闭和取消都必须释放预占库存；已支付取消不自动回滚库存，必须执行“人工退款确认”流程后再释放。
- 状态变更使用 order_status_log 保存操作者、来源、前后状态、原因和时间。
- 任何状态操作使用订单 version 做乐观锁；同一状态的重复请求返回成功但不重复记流水。

### 3.6 库存策略

库存表以规格为单位，维护 physical_stock_qty 和 reserved_qty：

| 事件 | physical_stock_qty | reserved_qty | 库存流水 |
| --- | --- | --- | --- |
| 创建订单 | 不变 | +下单数量 | RESERVE |
| 支付成功 | -下单数量 | -下单数量 | PAY_DEDUCT |
| 支付前取消/关闭 | 不变 | -下单数量 | RELEASE |
| 已支付取消并退款确认 | 不变 | 不变 | REFUND_RELEASE，必要时人工回补实物库存 |

创建订单使用条件更新：

~~~sql
UPDATE product_spec
SET reserved_qty = reserved_qty + #{quantity}
WHERE id = #{specId}
  AND status = 'ACTIVE'
  AND physical_stock_qty - reserved_qty >= #{quantity};
~~~

受影响行数为 0 时返回 STOCK_INSUFFICIENT。支付回调和库存变更放在同一数据库事务中，并通过幂等键防止重复扣减。

### 3.7 微信支付

1. 小程序登录通过 code2Session 获取 openid，不保存微信 session_key 到客户端。
2. 用户确认价格后，后端生成 out_trade_no，调用微信支付 JSAPI 预支付，返回小程序支付参数。
3. 回调接口使用 APIv3 平台证书验签，校验商户号、订单号、金额和币种。
4. 回调以 out_trade_no 和 transaction_id 唯一约束保证幂等；重复通知直接返回成功。
5. 支付成功事务：写支付记录、订单转 PAID_WAIT_DELIVERY、库存正式扣减、记录状态日志、发起通知。
6. 支付金额与订单 final_amount_cent 不一致时记录错误、拒绝更新订单，并保留原始通知用于人工排查。
7. 客户端支付结果只用于页面刷新，不能作为业务成功依据。

### 3.8 通知

一期使用微信小程序订阅消息，不使用短信。用户在下单前完成订阅授权，消息发送失败只记录不阻塞业务：

| 触发 | 接收方 | 模板意图 | 失败处理 |
| --- | --- | --- | --- |
| 订单创建 | 用户 | 订单已提交，等待商家确认 | message_log 记录失败原因 |
| 商家改价 | 用户 | 订单金额已更新，请确认并支付 | 同上 |
| 订单完成 | 用户 | 订单已配送完成 | 同上 |
| 新订单/新支付 | 商家 | 后台提醒和待处理数量 | 使用后台轮询，不发送短信 |

订阅模板 ID 和字段映射配置在 application.yml；测试环境使用 mock 通知客户端。

## 4. 数据字典与数据模型

### 4.1 通用约定

- 主键：BIGINT UNSIGNED，使用数据库自增；对外展示使用业务编号。
- 时间：DATETIME(3)，服务端统一存储 UTC 或 Asia/Shanghai，本文默认 Asia/Shanghai，所有读写使用同一时区。
- 软删除：只有商品、分类、轮播图使用 deleted；订单和支付记录禁止物理删除。
- JSON 字段仅用于地址快照、微信通知原文和文件元数据，不用于核心金额字段。
- 枚举在数据库中使用 VARCHAR(32)，Java 中使用 enum 并由服务端校验。

### 4.3 关键字段

#### admin_user

字段：id、username、password_hash、status、last_login_at、created_at、updated_at。username 唯一，password_hash 使用 BCrypt。

#### wx_user

字段：id、openid、nickname、avatar_url、status、last_login_at、created_at、updated_at。openid 唯一；禁止存储 session_key。

#### user_address

字段：id、wx_user_id、contact_name、phone、detail_address、is_default、created_at、updated_at。索引：(wx_user_id, deleted, is_default)。

#### product_category

字段：id、name、sort、status、deleted、created_at、updated_at。name 不区分大小写唯一；status 取 ACTIVE、DISABLED。

#### product

字段：id、category_id、name、subtitle、description、main_image_url、status、deleted、created_at、updated_at。status 取 ACTIVE、OFF_SHELF；商品可无规格，但不能发布无规格商品。

#### product_spec

字段：id、product_id、name、quantity_kind（PIECE/WEIGHT）、unit、price_cent、min_quantity、step_quantity、physical_stock_qty、reserved_qty、warning_qty、status、deleted、created_at、updated_at。  
约束：price_cent >= 0；数量为 DECIMAL(12,3)；physical_stock_qty >= 0；reserved_qty >= 0；reserved_qty <= physical_stock_qty。  
索引：(product_id, status)、(status, physical_stock_qty - reserved_qty) 可用作预警查询的冗余字段或视图。

#### shop_banner

字段：id、title、image_url、jump_type（NONE/PRODUCT/CATEGORY）、jump_target_id、sort、status、deleted、created_at、updated_at。用户端只返回 status=ACTIVE 且 deleted=0 的记录。

#### cart_item

字段：id、wx_user_id、product_spec_id、quantity、created_at、updated_at。唯一约束：(wx_user_id, product_spec_id)；quantity 大于 0。

#### sales_order

字段：

- id、order_no、wx_user_id、status、source、remark。
- address_snapshot JSON：contact_name、phone、detail_address。
- estimated_amount_cent、final_amount_cent、currency=CNY。
- quote_version、quoted_at、pay_deadline_at、paid_at、delivered_at、completed_at、closed_at、cancelled_at。
- cancel_reason、refund_status（NONE/REQUIRED/MANUAL_REFUNDED）、refund_reference、version。
- created_at、updated_at。

索引：order_no 唯一；(wx_user_id, status, created_at)；(status, pay_deadline_at)；(status, created_at)。

#### sales_order_item

字段：id、order_id、product_id、product_spec_id、product_name、spec_name、quantity_kind、unit、unit_price_cent、estimated_quantity、actual_quantity、estimated_amount_cent、final_amount_cent、product_image_url、created_at。  
约束：同订单订单项数量至少 1；actual_quantity 只能在改价阶段修改；金额为非负 BIGINT。

#### order_price_revision

字段：id、order_id、revision_no、previous_amount_cent、final_amount_cent、reason、items_snapshot JSON、adjusted_by_type、adjusted_by_id、created_at。唯一约束：(order_id, revision_no)。

#### payment_record

字段：id、order_id、out_trade_no、transaction_id、state（INIT/SUCCESS/FAILED）、amount_cent、trade_state、notify_raw JSON、paid_at、created_at、updated_at。唯一约束：out_trade_no；transaction_id 唯一且可为空。

#### stock_ledger

字段：id、product_spec_id、order_id、change_type（RESERVE/PAY_DEDUCT/RELEASE/REFUND_RELEASE）、quantity、physical_before、physical_after、reserved_before、reserved_after、biz_key、created_at。biz_key 唯一。

#### order_status_log

字段：id、order_id、from_status、to_status、operator_type（USER/ADMIN/SYSTEM/PAYMENT）、operator_id、reason、source、created_at。索引：(order_id, created_at)。

#### message_log

字段：id、wx_user_id、order_id、template_type、template_id、request_json、response_json、state、error_message、created_at。

#### operation_log

字段：id、admin_user_id、action、resource_type、resource_id、request_id、ip、result、created_at。

## 5. 接口设计

### 5.1 通用规范

- 基础路径：/api/v1；所有响应 JSON。
- 成功响应：{"code":"0","message":"ok","data":...,"traceId":"..."}。
- 失败响应：{"code":"ORDER_STATE_INVALID","message":"订单当前状态不允许此操作","traceId":"..."}。
- 分页参数：page 从 1 开始、pageSize 最大 100；返回 total、items。
- Token：Authorization: Bearer <token>；管理员和用户 Token 不可互用。
- 所有创建类接口支持 requestId 或 Idempotency-Key；支付和库存操作必须使用服务端幂等键。
- 字段名使用 camelCase；枚举使用大写英文；时间使用 ISO 8601 或 yyyy-MM-dd'T'HH:mm:ssXXX，服务端统一处理。

### 5.5 微信支付回调处理顺序

1. 验证微信平台证书、签名、时间戳、随机数和请求体摘要。
2. 解密资源，读取 out_trade_no、transaction_id、amount.total、trade_state。
3. 使用数据库事务查找支付记录；不存在时写入异常日志并返回错误。
4. 校验商户号、CNY、金额等于订单 final_amount_cent。
5. 通过唯一索引和状态条件更新支付记录；若已 SUCCESS，直接返回成功。
6. 订单状态更新、库存扣减、状态流水、通知任务在同一事务或可靠出站表中完成。
7. 返回 HTTP 200 和成功 JSON；重复通知不能重复扣库存。

## 7. 后端实现设计

### 7.1 分层

Controller -> Application Service -> Domain/Repository -> Mapper -> MySQL  
外部依赖通过 Port/Adapter 封装：WeChatLoginClient、WeChatPayClient、ObjectStorageClient、MessageClient。

Controller 只做鉴权、参数绑定、请求校验和响应映射。订单和库存事务放在 Application Service，禁止在 Controller、Mapper 或定时任务中拼接状态流转。

### 7.2 订单事务

创建订单：

1. 校验用户、地址和订单项。
2. 对订单项逐个预占库存，任意一项失败整体回滚。
3. 写 sales_order、sales_order_item、stock_ledger、order_status_log。
4. 建立 order_price_revision revision_no=0，记录原始预估金额。
5. 返回订单号和预估金额。

商家改价：

1. 使用 order_id + status + quote_version 条件更新锁定订单。
2. 校验订单项和最终金额。
3. 写入新 revision、更新订单 final_amount_cent、quote_version、quoted_at、pay_deadline_at。
4. 状态转 QUOTED，记录日志，加入通知队列。

支付成功：

1. 幂等查找支付记录。
2. 检查订单状态和金额。
3. 写 SUCCESS 支付记录和订单 PAID_WAIT_DELIVERY。
4. 每个订单项执行“扣减实物、释放预占”的条件更新，写 PAY_DEDUCT 流水。
5. 记录 paid_at，触发用户支付成功通知。

### 7.3 幂等和并发

- 订单创建使用客户端 idempotencyKey；重复请求返回同一 orderNo。
- 订单状态更新使用 version 条件更新。
- 支付记录 out_trade_no、transaction_id 唯一。
- 库存流水 biz_key 唯一，例如 PAY_DEDUCT:orderId:specId。
- 定时任务先查询到期记录，再按订单 id 逐个加锁处理，重复执行无副作用。
- 所有批量操作限流并记录操作日志。

### 7.4 错误码

| code | HTTP | 说明 |
| --- | --- | --- |
| AUTH_REQUIRED | 401 | 未登录或 Token 无效 |
| AUTH_FORBIDDEN | 403 | 无权访问资源 |
| VALIDATION_ERROR | 400 | 参数格式或业务字段错误 |
| PRODUCT_NOT_AVAILABLE | 409 | 商品不存在、下架或无有效规格 |
| STOCK_INSUFFICIENT | 409 | 可用库存不足 |
| ORDER_NOT_FOUND | 404 | 订单不存在 |
| ORDER_STATE_INVALID | 409 | 当前状态不允许操作 |
| QUOTE_VERSION_CONFLICT | 409 | 改价版本过期 |
| PAY_AMOUNT_MISMATCH | 409 | 回调金额和订单金额不一致 |

## 8. 安全、配置和运维

### 8.1 安全要求

- 密码只存 BCrypt hash；禁止明文、MD5 和日志打印密码/Token。
- JWT 使用强随机密钥，配置过期时间；用户 Token 7 天，管理员 Token 8 小时。
- 管理接口、文件上传、订单操作均写 operation_log。
- 微信回调证书、商户私钥和数据库密码只放环境变量或密钥管理服务。
- 上传文件校验扩展名、MIME、大小和文件魔数；对象存储路径加入 UUID，不接受任意路径。
- 所有 SQL 使用参数绑定；所有外部 URL 只能来自配置或对象存储返回。
- Nginx 启用 HTTPS、HSTS、基础请求体限制和访问日志；后端设置 CORS 仅允许管理域名。

### 8.2 配置项

deploy/.env.example 至少包含：

### 8.3 部署

1. Linux 服务器安装 Docker 和 Docker Compose。
2. 准备域名、HTTPS 证书、微信小程序 request 合法域名、支付回调域名和对象存储跨域配置。
3. 配置 .env，启动 mysql、backend、nginx；后台静态文件由 nginx 提供。
4. 执行 Flyway V1 创建表结构和 V2 初始化管理员。
5. 上传商品图片、创建分类和商品、发布轮播图，先用测试订单完成支付联调。
6. 使用 health endpoint 检查服务；查看 backend 日志、MySQL 慢查询和对象存储访问日志。
7. 每日备份数据库和关键配置；保留至少 7 天，恢复流程写入部署文档。

### 8.4 监控和日志

- /actuator/health 只暴露健康状态，不在公网暴露完整配置。
- 日志包含 traceId、orderNo、out_trade_no；禁止记录完整 openid、手机号、支付密钥。
- 关键告警：支付回调失败、库存条件更新失败、任务积压、数据库连接失败、对象存储上传失败。
- message_log、payment_record、stock_ledger、order_status_log 是排障依据，不允许通过普通管理界面删除。
